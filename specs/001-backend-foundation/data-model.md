# Foundation Data Model: Milestone 01

## Scope

Milestone 01 introduces no business entity, business table, or final ERD. Customers,
authentication, products, inventory, bundles, carts, orders, payments, shipping, reviews, and all
other commerce records remain out of scope. PostgreSQL may contain only Prisma-managed migration
metadata until a later approved feature introduces its owned schema.

This document defines transient operational structures and state contracts needed to implement and
test the foundation.

## Persistent Database State

### Prisma Migration Metadata

**Owner**: Prisma migration tooling

**Purpose**: Record which committed migrations have been applied to a database.

**Rules**:

- Application code MUST NOT read or write migration metadata directly.
- Startup MUST NOT apply or repair migrations.
- Migration history is changed only by the documented Prisma 7 commands.
- An applied migration file MUST NOT be edited; a correction uses a new migration or an explicitly
  reviewed incident recovery procedure.
- No project-defined table is created in this milestone.

## Runtime Configuration Contract

### EnvironmentConfiguration

An immutable in-memory value created before application startup.

| Field | Type | Required | Validation | Sensitive |
| --- | --- | --- | --- | --- |
| `nodeEnv` | enum | Yes | `development`, `test`, or `production` | No |
| `port` | integer | Yes or safe documented default | 1 through 65535 | No |
| `databaseUrl` | URL string | Yes | PostgreSQL scheme; credentials and database name present; test safety rules apply in test mode | Yes |
| `logLevel` | enum | Yes or safe documented default | Supported Pino level | No |
| `databaseStartupTimeoutMs` | integer | Yes or default 5000 | 1000 through 10000 | No |
| `databaseProbeTimeoutMs` | integer | Yes or default 1000 | 100 through 1500 so the endpoint remains below two seconds | No |
| `shutdownTimeoutMs` | integer | Yes or default 8000 | 1000 through 9000 | No |

**Validation rules**:

- Validation completes before any listener binds.
- All owned-key violations are returned together where safe.
- Diagnostics identify a key and expected format, not its supplied secret value.
- `databaseUrl` is never serialized into logs, error bodies, health bodies, or OpenAPI examples.
- In test mode, database names MUST end in `_integration` or `_e2e` for database-backed suites.
- Production configuration MUST refuse any local-only reset or cleanup command.

## Request Context

### CorrelationContext

An in-memory request-scoped value.

| Field | Type | Validation |
| --- | --- | --- |
| `correlationId` | UUID string | Caller value accepted only when it is one valid UUID; otherwise generated by the server |
| `method` | HTTP method | Allowlisted method token |
| `route` | normalized route template/string | Query string and credentials excluded |
| `startedAt` | monotonic timestamp | Server generated |

**Rules**:

- `correlationId` is returned through `X-Correlation-ID` and included in safe error bodies.
- Request bodies, query strings, cookies, authorization headers, and arbitrary headers are not part
  of the logging context.
- Context ends when request processing ends and MUST NOT leak between concurrent requests.

## Health Contracts

### LivenessResponse

| Field | Type | Allowed value |
| --- | --- | --- |
| `status` | string enum | `ok` |

Liveness does not query PostgreSQL. A successful response means only that the process can handle the
probe.

### ReadinessResponse

| Field | Type | Allowed value |
| --- | --- | --- |
| `status` | string enum | `ok` |
| `checks` | object | Required |
| `checks.database` | string enum | `up` |

The success shape is returned only after a fresh bounded database probe succeeds.

### ErrorResponse

The shared safe error envelope for readiness failure and other HTTP errors.

| Field | Type | Required | Rules |
| --- | --- | --- | --- |
| `statusCode` | integer | Yes | Matches the HTTP status |
| `code` | string | Yes | Stable uppercase machine code |
| `message` | string | Yes | Safe public text; no raw internal cause |
| `correlationId` | UUID string | Yes | Matches `X-Correlation-ID` |
| `details` | array/object | No | Validation information only; never rejected secret values |

**Foundation codes**:

| HTTP status | Code | Usage |
| --- | --- | --- |
| 404 | `ROUTE_NOT_FOUND` | No route exists for the requested path/version |
| 503 | `SERVICE_UNAVAILABLE` | Readiness database probe failed or service is shutting down/unready |
| 500 | `INTERNAL_ERROR` | Unclassified internal failure; cause remains in protected redacted logs only |

## Runtime State Model

### ApplicationAvailability

This state is process-local operational state, not persisted business data.

| State | Meaning | Liveness | Readiness | Non-health application traffic |
| --- | --- | --- | --- | --- |
| `STARTING` | Config valid; database startup probe incomplete | No listener | No listener | Not accepted |
| `READY` | Startup probe or latest fresh runtime probe succeeded | 200 | 200 | Allowed subject to route rules |
| `DEGRADED` | Runtime database probe or operation failed | 200 | 503 | Rejected with safe 503 |
| `SHUTTING_DOWN` | Termination accepted; drain has begun | May remain 200 during short drain | 503 | New work rejected |
| `STOPPED` | Listener and database resources closed | No listener | No listener | Not accepted |

### State Transitions

```text
STARTING --successful bounded DB probe--> READY
STARTING --failed/timeout DB probe------> STOPPED (non-zero startup exit)
READY ----failed/timeout DB probe-------> DEGRADED
DEGRADED -successful fresh DB probe-----> READY
READY ----termination-------------------> SHUTTING_DOWN
DEGRADED -termination-------------------> SHUTTING_DOWN
SHUTTING_DOWN --clean bounded close-----> STOPPED
SHUTTING_DOWN --timeout-----------------> STOPPED (forced/non-zero outcome)
```

**Invariants**:

- The HTTP listener is not bound while `STARTING`.
- A readiness success is never returned from cached startup state; it requires a fresh probe.
- A database failure cannot transition directly to `READY` without a subsequent successful probe.
- `SHUTTING_DOWN` cannot transition back to `READY`.
- Every transition emits a structured, redacted event only when the state actually changes.

## Migration Artifact Model

### MigrationArtifact

A version-controlled file set rather than an application entity.

| Attribute | Requirement |
| --- | --- |
| Identifier | Prisma timestamp/name generated by the approved development command |
| SQL | Human-reviewed, deterministic, and committed |
| Checksum/history | Managed by Prisma and validated against applied history |
| Risk notes | Required in the change description for locking, destructive, or data-reinterpreting work |
| Recovery approach | Required before applying a risky migration |

**Lifecycle**:

```text
Schema change -> create-only migration -> SQL review -> development apply -> empty-database replay
-> repeat deploy/status validation -> merge -> later environment deployment
```

`db push`, application-startup migration, and non-local reset are not valid lifecycle transitions.

## Test Database Ownership

| Database | Owner | Allowed use |
| --- | --- | --- |
| `nordhaven` | Local developer | Manual development only |
| `nordhaven_integration` | Integration suite | Prisma/PostgreSQL behavior; serial suite |
| `nordhaven_e2e` | E2E/process suite | Full application HTTP and lifecycle behavior; serial suite |

Test setup MUST validate `NODE_ENV=test`, host allowlisting, and the exact database suffix before
reset or cleanup. A failed guard stops the suite without changing any database.
